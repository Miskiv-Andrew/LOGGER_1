Краткое описание системы "ДРОН-1":

	- самая простая модель из тех, что планируются - на борту 1(один) БДБГ-15, LIDAR, GPS, RadioLine().
	  Работа в условиях спуфинга или наличия активной РЭБ не планируется. Работа с 2(вторым) БДБГ-15 и
	  использованием коллиматоров не планируется. Использование StarLink и видеокамеры не планируется.
	  
	  Добавление в следующих версиях 2 (второго) БДБГ-15 принципиально не изменит машину состояний,
	  добавится опрос еще одного БДБГ-15

Задачи системы "ДРОН-1":

	- производить радиационную разведку в заданном районе
	- онлайн передавать на приемную станцию радиационные данные,
	  "привязанные" к конкретной точке с указанными координатами
	  и высотой над поверхностью:
		
	- сохранять пакеты данных на SD-карту ( отправленные и переданные пакеты идентичны 
	                                        для простоты обработки )
											
	- иметь возможность принимать команды с приемной станции и 
	  обрабатывать их ( списки и форматы команд приведены в конце документа)
	  
	- производить трассировку всего маршрута

Возможные варианты проведения разведки

	В любом из вариантов оператор разведки в начале работы (до запуска дрона)
	должен выбрать область разведки на карте. Эта область потом будет загружена
	в память дрона после проведения предполетной диагностики. Максимальное кол-во
	точек для описания полигона - 20. Полигон должен быть выпуклым.
	Управление полетом дрона выполняет оператор дрона. 
	Радиационную разведку выполняет оператор радиационной разведки. 
	Выполнение разведки без загруженной области разведки невозможно.
	
	Во всех режимах разведки дрон с определенным интервалом опрашивает GPS 
	(для трассировки пути) и независимо от режима работы передает на землю свои координаты. 
	
	1.  Работа по командам оператора ( А )
			- Полный цикл опроса с данными приборов дрон выполняет
			  только по команде с земли.
		  
	2.  Работа по временным меткам ( В )(сохранение данных с определенным временным интервалом)
			- После захода в зону разведки мы производим полный цикл опроса и 
			  начинаем контроль тиков(секунд) таймера RTC. При истечении заданного временного 
			  интервала от последнего момента сохранения производим полный цикл опроса
			  с данными приборов. Алгоритм повторяется до тех пор, пока дрон находится в 
			  зоне разведки.
		  
	3.  Работа по маршруту ( С )(сохранение данных с определенным расстоянием между точками)
			- После захода в зону разведки мы производим полный цикл опроса и 
			  начинаем контроль расстояния между последней сохраненной точкой и текущим положением.
			  Как только расстояние становится больше заданного, производим полный цикл опроса
			  с данными приборов. Алгоритм повторяется до тех пор, пока дрон находится в 
			  зоне разведки.	
			  
			  
	4.  Набор спектра ( D ) (получение спектра в конкретной точке области разведки )
			- После получения команды с земли "Начать набор спектра" ( дрон к моменту
			  получения команды должен зависнуть в данной точке ) мы начинаем набор
			  и аддитивное суммирование отсчетов спектра. После окончания набора 
			  ( истекло время набора или пришла команда с земли) результирующий массив
			  записывается на SD-карту
			  
			  
	Для описания вариантов проведения разведки введем 
	
	typedef enum {    
	
		DWM_DEFAULT,             // Начальное значение
		MODE_OPERATOR,       // Работа по командам оператора (А)
		MODE_TIME,           // Работа по временным меткам (B)
		MODE_DISTANCE,       // Работа по маршруту(дистанция между точками) (C)
		START_SPECTRE,       // Старт набора спектра
		MODE_SPECTRE,        // Получение кадра спектра
		
	} DroneWorkMode drone_work_mode; 
	  DroneWorkMode old_work_mode; // необходима для фиксации текущего состояния,    
                                   // чтобы потом вернуться в него при необходимости     

  
	Объявим глобальную переменную времени набора спектра	
	и присвоим ей значение по умолчанию
	
	uint16_t load_spectre_time = 0;
	
	Набор спектра может осуществляться либо по заданному времени (сек)  load_spectre_time > 0
	либо по команде с земли                                      тогда  load_spectre_time == 0

Работа с прерываниями приборов ( USART, ADC ):

	Для всех приборов на борту принцип работы с использованием прерываний одинаков:
	
		- объявляем глобальные флаги наличия данных  (uint8_t)
		       bdbg_info, 
		       lidar_info, 
			   gps_info, 
			   battery_info
	
		- USART-ы и  ADC отключены, включаем только в момент опроса
		- при необходимости работы с тем или иным прибором мы заходим в состояние REC_...
		   REQ_BATTERY, REQ_BDBG, REQ_GPS, REQ_LIDAR 
		   
		- в этих состояниях:
			- включаем соответствующий интерфейс
			- сбрасываем   флаг наличия данных == false(0)
			- запускаем таймер контроля неответа прибора на соответствующее время
			- переменной DevType dev_type присваиваем соответствующее значение данного прибора
			- выполняем действия, необходимые для конкретного прибора 
			  ( в БДБГ, например, выполняем нужный запрос)
			  
		- переходим в состояние обработки ответа прибора  ...PROC		
		    BATTERY_PROC, BDBG_PROC, LIDAR_PROC, GPS_PROC
			
		- непосредственно в обработчике прерываний выполняем контроль
		  готовности к обработке ( принято нужное кол-во байт, и т.д.)
		  Когда возникает готовность - сбрасываем флаг прерывания,
		  поднимаем флаг наличия данных ..._info

			Общий вид начала обработчика данных прибора ...PROC 
			
			if(drone_state == ...PROC) // Выбор конкретного состояния
			{
				HAL_Delay(1);    //  Для разгрузки камня
				if(..._info) {   //  Если есть "сырые" данные для обоработки
				
					..._info = 0 (false);  // Сбрасываем флаг наличия данных
					...                    //останавливаем таймер контроля неответа прибора
				    	
					...                  // Здесь проводим обработку данных прибора		
				    ...	                 // и последующие действия 			
				}
				else { // нет данных для обработки
				
					/*
						Здесь мы сидим, пока нет данных,
						которые мы ожидаем
						Для избегания невыхода из состояния ( если 
						что-то пошло не так и флаг наличия данных не поднялся)
						используем таймер контроля неответа прибора - если таймер 
						неответа прибора сработает - значит, что-то пошло не так. 
						Таймер переключит состояние в нужное для корректного 
						продолжения работы						
					*/				
				}
			}

Работа с прерываниями командной радиолинии ( USART):

		объявляем глобальный флаг наличия данных 
		bool com_info, 
	
		Алгоритм работы тот же, отличие только в том,
		что USART_CommandLine никогда не выключается.
		
		В основном мы сидим в состоянии COMMAND_INFO, выходим из него
		только для опроса данных, формирования пакета, записи данных
		на карту и передачи на землю.
		Если в момент проведения опроса с земли прилетит команда - ОК,
		она будет ждать обработки в состоянии COMMAND_INFO
		
		Работа радиолинии описана в разделе "Работа радиолинии"

Работа радиолинии

	ЗЕМЛЯ - ДРОН
	
	ФОРМАТ ПАКЕТА:
	
		Start bytes (4 байта)
			- Маркер начала пакета 0xAA 0x55 0xAA 0x55
			
		Command ID (1 байт)		
			- Идентификатор команды 
			
		Length (2 байта, uint16_t)
			- Длина поля Payload в байтах
			
		Payload (N байт)
			- Данные команды
			  Прим: если данные отсутствуют(используем только идентификатор команды), 
			        Length = 0x0001, Payload = 0x01
					
		Checksum (2 байта)
			- Контрольная сумма (например, CRC16)
			- Рассчитывается по всему пакету, кроме стартовых и конечных байт
			
		End bytes (4 байта)
			- Маркер окончания пакета 0x0D 0x0A 0x0D 0x0A
			
			
	ОТПРАВКА ПАКЕТА:
	
		Пакет будет 2-х кратно продублирован , т.е. будут передаваться подряд
		2 одинаковых пакета без паузы между пакетами ( или больше пакетов, 
		если коэффициент дублирования на земле будет увеличен)
		
	АЛГОРИТМ РАБОТЫ ПРИЕМНИКА(ДРОН):		
		  
		- при получении байта ( возникает прерывание по USART_CommandLine ) запускаем таймер работы
          с радиолинией на 0.1 сек ( перезапускаем каждый раз при приеме очередного байта). 
		  При скорости передачи 9600 кБит/сек интервал между байтами около 1 мсек - срабатывание таймера
		  с интервалом 0.1 сек означает, что передача с земли закончена и "прилетел" весь пакет. 
		  Принятые байты записываем в буфер
		
		- Обработка принятых с земли команд происходит только в состоянии COMMAND_INFO - глобальный флаг наличия
		  новой информации в радиолинии bool com_info = true(1) должен быть поднят в прерывании таймера
		  работы с радиолинией (описание работы таймера радиолинии приведено ниже)
		  
		- При заходе или пребывании в состоянии COMMAND_INFO и поднятом флаге com_info == true(1) 
		  начинаем обработку буфера:
		  
			- сбрасываем com_info = false(0)
			
			- если длина буфера < 14 байт:
				- очищаем буфер
				- передаем на землю "Пакет не принят"
				- далее в зависимости от режима работы (состояние COMMAND_INFO будет описано 
				                                        ниже в машине состояний )
			- если длина буфера >= 14 байт:	
				- ищем начало пакета (0xAA 0x55 0xAA 0x55) и окончание пакета (0x0D 0x0A 0x0D 0x0A) 
				  с условием - между началом и концом не должно быть еще одного начала, если мы нашли
				  начало пакета и при поиске окончания пакета наткнулись на еще одно начало - начинаем поиск окончания
				  пакета заново с нового начала пакета; 
				  если при поиске начала мы наткнулись на окончание пакета, но при этом не нашли начало - значит,
				  прилетел обрывок, удаляем все до обрывка и окончание обрывка и приступаем к поиску заново;
				- выделяем все байты между началом и окончанием пакета
				- рассчитываем контрольную сумму
				- если сумма не совпала, удаляем найденное начало, конец и все байты между ними и повторяем поиск,
				- если не удалось найти валидный пакет:
					- очищаем все буферы					
					- передаем на землю "Пакет не принят"
					- далее в зависимости от режима работы (состояние COMMAND_INFO будет описано 
				                                        ниже в машине состояний )
					
				- если сумма совпала, пакет валидный
					- обрабатываем и сохраняем данные
					- очищаем все буферы
					- передаем на землю "Пакет принят"					
					- далее в зависимости от режима работы (состояние COMMAND_INFO будет описано 
				                                        ниже в машине состояний )  
				  
			
			
		Прим: здесь описана обобщенная схема обработки просто для понимания, варианты принятых
        команд и обработка описаны в COMMAND_INFO	

		Прим: ДРОН в любом случае отвечает на прием команды с земли ( ПРИНЯЛ, НЕ ПРИНЯЛ) - команды 
		ДРОНа описаны ниже
			
	                                    ТАБЛИЦА КОМАНД ЗЕМЛЯ - ДРОН
	
			ID		Команда                                             Наличие данных в пакете ( Payload )
			-----------------------------------------------------------------------------------------------
			
			01		Провести предполётное тестирование                      default value 
			
			02		Продолжить разведку без SD-карты                        default value
			
			03		Не продолжать разведку без SD-карты                 	default value
			
			04		Получить параметры разведки                             +    ( FlightConfig )
			
			05		Изменить коэффициент дублирования пакетов               +    ( uint8_t )
			
			06		Изменить время между измерениями                        +    ( uint16_t )
			
			07		Изменить дистанцию между измерениями                    +    ( uint16_t )
			
			08		Закончить разведку                                      default value
			
			09		Изменить режим разведки                                 +    ( uint8_t ) 
			
			10		Произвести измерение (ручной режим)                     default value
			
			11		Изменить время набора спектра                           +    ( uint16_t )
			
			12		Прекратить набор спектра                                default value
			
			13		Перейти в режим радиомолчания                           default value
			
			14		Выйти из режима радиомолчания                           default value

	ДРОН - ЗЕМЛЯ			                                   Command ID(2 bytes);	Length(4 bytes); Payload (Nx2 bytes)\n   -  формат файла .CSV
				  
	Объявим uint8_t write_radioline_flag = 1;
		1 - (все ОК)   - передаем данные в эфир
		0 - (проблемы) - не передаем данные в эфир ( режим радиомолчания )
				  
	АЛГОРИТМ РАБОТЫ ПЕРЕДАТЧИКА(ДРОН):
	
	ФОРМАТ ПАКЕТА:  (полностью аналогичен пакету с земли)
	
		Start bytes (4 байта)
			- Маркер начала пакета 0xAA 0x55 0xAA 0x55
			
		Command ID (1 байт)
			- Идентификатор команды 
			
		Length (2 байта, uint16_t)
			- Длина поля Payload в байтах
			
		Payload (N байт)
			- Данные команды
			  Прим: если данные отсутствуют(используем только идентификатор команды), 
			        Length = 0x0001, Payload = 0x01
					
		Checksum (2 байта)
			- Контрольная сумма (например, CRC16)
			- Рассчитывается по всему пакету, кроме стартовых и конечных байт
			
		End bytes (4 байта)
			- Маркер окончания пакета 0x0D 0x0A 0x0D 0x0A			
			
	ОТПРАВКА ПАКЕТА:
	
		Объявим переменную количества дублирования пакетов		
		uint8_t repeat_factor = 2;  
	
		Пакет будет 2-х кратно продублирован , т.е. будут передаваться подряд
		2 одинаковых пакета (или больше если коэфициент дублирования дрона 
		uint8_t repeat_factor увеличен) без паузы между пакетами
				
	АЛГОРИТМ РАБОТЫ ПЕРЕДАТЧИКА (ДРОН):

		- за основу берем массив ARR данных для передачи  ( это Payload )
		- в зависимости от типа и размера передаваемого пакета вставляем Command ID (1 байт) и Length (2 байта).
		- Рассчитываем контрольную сумму (CRC16, 2 байта) полученного массива и вставляем в конце масива	
		- перед ARR вставляем 0xAA 0x55 0xAA 0x55 (Start bytes)
		- после ARR вставляем 0x0D 0x0A 0x0D 0x0A (End bytes)

ОБРАБОТЧИК ТАЙМЕРА РАБОТЫ С РАДИОЛИНИЕЙ

	Таймер работы с радиолинией запускается каждый раз при возникновении прерывания по приему байта
	в USART_CommandLine

	Во всех режимах (MODE_TEST, MODE_EXPECT, MODE_WORK) обработка в прерывании таймера радиолинии одинаковая:
		- остановить таймер работы с радиолинией
		- cбросить все необходимые флаги( прерываний и т.д.)
		- выставить глобальный флаг наличия принятой команды  bool com_info = true(1)
	
--------------------------------------------------------------------------------------------------------------------

ОБРАБОТЧИК ТАЙМЕРА КОНТРОЛЯ НЕОТВЕТА ПРИБОРОВ

		Таймер нужен для предотвращения зацикливания кода при неответе или невалидном ответе прибора.
		Запускается таймер в состояниях REQ... в начале работы с прибором
		Если прибор ответил корректно, останавливаем таймер, дальше по алгоритмам...
		Если таймер сработал - значит, что-то пошло не так. 
		Для использования таймера контроля неответа приборов  введем 
		
		typedef enum {
				TYPE_BDBG,
				TYPE_BATTERY,
				TYPE_LIDAR, 
				TYPE_GPS,     
				TYPE_SD,
				TYPE_COMMANDLINE
			} DevType;

		DevType dev_type - в начале каждого старта таймера при работе с конкретным прибором глобальной
		переменной dev_type присваиваем  соответствующее значение, при срабатывании таймера
		контроля неответа приборов понимаем с каким прибором проблемы
		

	если тестовый режим :  req_mode == MODE_TEST
	
		- Если dev_type == TYPE_BATTERY (проверка батареи)
			- отключить таймер контроля ответа прибора	
			- отключить	АЦП		
			- отправить в радиолинию сообщение о неответе прибора ("Аккумулятор неисправен, разведка невозможна")
			- перейти в состояние COMMAND_INFO	  drone_state = COMMAND_INFO 
				  (будем ожидать, что заменят батарею и начнут тестирование сначала) 
				  
				  
		- Если dev_type == TYPE_BDBG ( БДБГ не ответил, пришло недостаточно байт и т.д. ):
				- отключить таймер контроля ответа прибора
				- отключить USART_БДБГ
				- очистить приемный буфер USART_БДБГ				
				- отправить в радиолинию сообщение о неответе прибора ("БДБГ-15 не ответил на запрос")
				- перейти в состояние COMMAND_INFO	  drone_state = COMMAND_INFO 
				  (будем ожидать, что БДБГ приведут в порядок и начнут тестирование сначала )

		- Если dev_type == TYPE_LIDAR ( LIDAR не ответил, не удалось выделить валидный пакет и т.д. ):
				- отключить таймер контроля ответа прибора
				- отключить USART_LIDAR
				- очистить приемный буфер USART_LIDAR				
				- отправить в радиолинию сообщение о неответе прибора ("LIDAR неисправен(нет передачи данных)")
				- перейти в состояние COMMAND_INFO	  drone_state = COMMAND_INFO 
				  (будем ожидать, что LIDAR приведут в порядок и начнут тестирование сначала )
				  
				  
		- Если dev_type == TYPE_GPS ( GPS не ответил, не удалось выделить валидный пакет и т.д. ):

				- отключить USART_GPS

				- перейти в состояние COMMAND_INFO	  drone_state = COMMAND_INFO 
				  (будем ожидать, что GPS приведут в порядок и начнут тестирование сначала, или просто ждем

Работа с неисправностями приборов:

		Исходим из того, что в процессе добирания до области разведки и при проведении разведки
		могут произойти сбои в работе и выходы приборов из строя. Перечислим возможные ситуации:
		
		Батарея:
			- проблемы с прерыванием в АЦП ( не срабатывает прерывание , не имеем данных напряжения )
			- падение напряжения ниже допустимого не рассматриваем как выход из строя -
			  на земле по принятым данным производим перерасчет и выводим оператору разведки
			  время в минутах до отключения батареи и логгера
		
		БДБГ:
			- неответ
			- некорректный ответ ( CRC not valid, недостаточно байт )
			- поломка высокочувствительного и (или) низкочувствительного датчиков
			
		LIDAR:
			- неответ
			- некорректный ответ ( не получается выделить валидный пакет )
			
		GPS:
			- неответ
			- некорректный ответ ( не получается выделить валидный пакет )
			- выявление спуфинга ( по сути, неработоспособность GPS )
			
	Также понимаем, что 1 некорректный ответ или неответ прибора не означает его неисправность.
	Механизм обработки проблем следующий:
	
		- для каждого прибора вводим uint8_t DEV_error_counter 
		( bdbg_error_counter, gps_error_counter, lidar_error_counter, batt_error_counter)
		
		- при некорректной работе прибора мы будем заходить в состояние проблем с прибором DEV_ERROR_PROC ( BDBG_ERROR_PROC,
		  GPS_ERROR_PROC  и т.д.), инкрементировать соответствующий счетчик поломок и проверять его;
		  
		- если значение соответствующего счетчика поломок не превысило значение 3, просто выходим из текущего цикла
		  опроса, больше ничего не предпринимаем ( описано в соответствующих состояниях )
		  		  
		- если значение соответствующего счетчика поломок превысило значение 3, дальнейшее проведение разведки 
		  становится невозможным, переходим в режим DRON_ERROR  MODE_ERROR и отправляем в радиолинию сообщение 
		  "Дальнейшее проведение разведки невозможно, прибор ..."

		Прим: все будет описано в соответствующих состояниях
		
		Прим: цифра 3 взята с потолка - в процессе тестирования подберем логичное значение
		  
		Прим: пока попробуем работу без перезагрузки GPS и LIDAR, после получения первых результатов добавим
		      дополнительные возможности в машину состояний и код

**Первичная проверка аккумулятора и SD-карты при включении питания LOGGER**

Первичная проверка выполняется однократно после включения питания LOGGER, после инициализации необходимой периферии, но до 
входа в основной цикл while(1) и начала работы стейт-машины.

**1. Проверка аккумулятора**

Микроконтроллер выполняет 10 последовательных измерений напряжения аккумулятора через ADC1 (вход PC1). 
Полученные значения усредняются, после чего вычисляется среднее напряжение на входе 
ADC с учётом опорного напряжения 2,5 В и 12-битного разрешения АЦП.

В зависимости от измеренного напряжения устанавливается состояние трёх светодиодов:

- U ≥ 0,915 В — включены PA15, PA12, PA11 (100%).
- 0,855 В ≤ U < 0,915 В — включены PA15, PA12 (66%).
- 0,824 В ≤ U < 0,855 В — включён PA15 (33%).
- U < 0,824 В — все три светодиода выключены.
- При ошибке измерения ADC все три светодиода также остаются выключенными.

Логическая 1 включает соответствующий светодиод, логический 0 выключает.

**2. Проверка наличия SD-карты**

Выполняется монтирование файловой системы SD-карты с использованием FatFs.

Если функция f_mount() возвращает FR_OK, включается светодиод PC13 (логическая 1).

Если монтирование завершилось ошибкой, PC13 остаётся выключенным (логический 0).

Данная проверка подтверждает доступность файловой системы SD-карты, но не проверяет возможность записи данных.

Результат монтирования передаётся модулю SD_Logger для последующего использования.

**3. Время визуального контроля**

После выполнения проверок LOGGER выдерживает паузу 60 секунд, в течение которой светодиоды отображают результаты проверки аккумулятора и SD-карты.

За это время оператор может оценить состояние аккумулятора и наличие SD-карты. При необходимости оператор отключает питание для устранения обнаруженных проблем.

По истечении 60 секунд все четыре светодиода (PA15, PA12, PA11, PC13) выключаются.

После этого запускается основной цикл while(1), и стейт-машина LOGGER начинает работу с исходного состояния COMMAND_INFO в режиме MODE_TEST.

Первичная проверка больше не повторяется до следующего включения питания LOGGER.

-----------------------------------------------------------------------------------------------------------------------	


	Прим: Работа с БДБГ
	
	Рабочие запросы БДБГ:
			- запрос ПАЕД
			- запрос температуры
			- команда на начало набора спектра
			- запрос на выдачу спектра
			
	Опишем тип запроса БДБГ структурой 
	
		typedef struct {			
			PAED_REQ;
			TEMP_REQ;			
			START_SPECTRE_REQ;
			GET_SPECTRE_REQ;			
		} BdbgMode;
					
			
	Создадим структуру для работы с запросами БДБГ	
		typedef struct {
			uint8_t deviceAddr;        // адрес прибора ( пока 1, когда будет 2 БДБГ в комплекте, используем это)
			BdbgMode bdbgMode;        // тип запроса, который сейчас будет производиться
			uint8_t expectedLength;    // ожидаемая длина ответа - для контроля длины пакета в прерываниях			
		} BdbgReq;
		
		Опишем константные массивы запросов: ( вставить сюда данные из протокола БДБГ-15 )
		const uint8_t req1[] = {0x01, 0x02, 0x03, 0x04};
		...
		...                                     
		
		при конкретном вопросе записать в глобальную BdbgReq bdbg_req = {...};
		и юзать ее в прерываниях и в обработке принятого пакета
		
		при работе с БДБГ необходимо помнить, что в начале и конце пакета
		могут быть мусорные байты - нужно искать начало пакета (0x55,0xAA) и от него считать принятые байты, 
		лишние отбрасывать (специфика работы DMA)  - в обработчике прерываний USART_БДБГ мы всегда знаем, сколько
		должно прилететь байт - ищем начало пакета 0x55,0xAA и от него считаем кол-во байт. Когда прилетело столько,
		сколько нужно, прекращаем обработку, сбрасываем флаги прерываний, отключаем USART_БДБГ, поднимаем флаг наличия данных
		bdbg_info...
		
		2 ВАРИАНТА РАБОТЫ С БДБГ-15
		
		1. Обычная разведка с измерением ПАЕД:
			- нормальный режим, дрон перемещается по координатам или высоте, набирает
			  пакет данных, отправляет на базу ...
			  
		2. Набор спектра:
			- дрон должен "зависнуть" в точке и получить команду с земли - "Начать набор спектра".
			  Логгер отправляет в БДБГ команду на набор спектра и затем с определенным интервалом (2-10 сек)
			  отправляет запросы в БДБГ на выдачу спектра. Спектр представляет собой массив размером 1024 uint16_t.
			  Спектр накапливается аддитивно, т.е. после получения очередного ответа прибора полученный массив
			  почленно суммируется с накопленными предыдущими. Сохранять спектр на SD-карте при каждом получении 
			  не имеет смысла. Каждый полученный пакет передается в радиолинию (для суммирования на земле).
			  Прекращение набора спектра происходит при записи запроса ПАЕД в БДБГ - прибор перестает набирать 
			  спектр и отдает значение ПАЕД.
			  		  
			  Сигналом для начала набора спектра есть:
				- команда с земли 
			  
			  Сигналом для прекращения набора спектра может быть:
				- команда с земли 
				- истекло время набора спектра 
				 ( время набора спектра по умолчанию 60 сек, командой с земли можно будет передать другое значение )
				 
			  После того, как набор спектра был прекращен, результирующий массив с координатами и высотой
			  точки набора и необходимыми параметрами сохраняется на SD-карте и дрон возвращается в тот 
			  режим разведки, в котором был до команды на набор спектра. Передавать этот "последний"
			  кадр на землю не нужно - там и так есть данные спектра, переданные по частям

	валидного пакета. Значение VALUE определим на практике
	
	- в самом обработчике прерывания USART_LIDAR:
		- записываем принятый байт в исходный буфер
		- проверяем кол-во байт в буфере
		- если кол-во принятых байт >= VALUE:
			- сбрасываем счетчик принятых байт
			- сбрасываем флаг прерываний USART_LIDAR
			- поднимаем флаг наличия информации LIDAR  lidar_info
			- отключаем USART_LIDAR ( пакеты LIDAR короткие и идут достаточно быстро,
			                          в донаборе не вижу смысла, 30-50 байт достаточно)
			
									  
	- в LIDAR_PROC:
		- если поднят флаг наличия информации LIDAR:
			- отключить таймер контроля ответа прибора
			- очистить приемный буфер USART_LIDAR
			- сбросить все необходимые флаги
			- сбрасываем флаг наличия информации LIDAR  lidar_info
			- начинаем обработку исходного буфера:
			
	Прим: "помним" 	текущие и прошлые данные для сравнения	изменения по высоте
			
			Далее в описании состояния LIDAR_PROC в зависимости от режима работы ...

					- переходим в состояние REQ_BDBG
				
				- если нет ( drone_work_mode != START_SPECTRE )
					- проводим сравнение параметров текущей точки с последней сохраненной:
						- используя текущую и прошлую пару координат, находим расстояние
						  между точками
						- используя текущую и прошлую высоты, находим разницу в высотах

								- передать в радиолинию сообщение ("Измерения для данной точки уже проведены")	
								
							- нет смысла сохраняться, переходим в состояние drone_state = COMMAND_INFO						
							
						- если расстояние >= заданного минимума ИЛИ разница в высотах >= заданного минимума: 
							- записать в drone_state = {1, 12, PAED_REQ}
							- переходим в состояние REQ_BDBG 
				
			- Если не удалось выделить корректный пакет LIDAR:
				
				- переходим в состояние LIDAR_ERROR_PROC

Работа с GPS:

	- помним, что после включения питания для выхода в режим GPS требуется 
	  некоторое время, необходимо выдержать некую паузу после включения питания;

	- кроме непосредственно измерений, GPS должен контролировать следующие параметры:
	
		- нахождение в области разведки либо вне области разведки
			Текущая координата проверяется на вхождение или невхождение в область разведки
			
		- нахождение в одной точке - постоянно сохраняем 2 координаты - прошлую и текущую, 
		  и получаем расстояние между ними:
			- если расстояние между точками < заданного минимума  ( дрон на месте) 
			- если расстояние между точками > заданного минимума  ( дрон перемещается, расстояние адекватное) 
			-  если расстояние между точками >> заданного минимума ( нереальное расстояние означает возможное
			   наличие спуфинга) - значение текущей координаты не сохраняем, инкрементируем счетчик 
			   наличия спуфинга; каждую вновь полученную координату сравниваем с последней валидной;
			   если спуфинг будет зафиксирован 3 раза, передать в радиолинию сообщение 
			   ("Зафиксирован спуфинг, разведка невозможна") и перейти в состояние MODE_ERROR 
			   
		- если значение новой координаты валидное, расстояние между точками сохраняем для 
		  принятия решения по сохранению данных: если расстояние между текущей точкой и последней
		  сохраненной точкой слишком мало, прерываем цикл опроса, сохранение не производим
		  

		- координата для трассировки маршрута
			В режиме тестирования ( ReqMode == MODE_TEST) трассировка маршрута не проводится
			В режиме ожидания разведки ( ReqMode == MODE_EXPECT) трассировка маршрута проводится
			(для инициализации запросов будем использовать RTC таймер)
			В режиме работы отдельно трассировка не проводится, данные координат передаются 
			в общем пакете данных вместе с данными измерений
			  
Обработчик GPS:

	За основу берем минимальное количество байт VALUE , необходимое для обработки данных и получения 
	валидного пакета. Значение VALUE определим на практике
	
	- в самом обработчике прерывания:
		- записываем принятый байт в исходный буфер
		- проверяем кол-во байт в буфере
		- если кол-во принятых байт >= VALUE:
			- сбрасываем счетчик принятых байт = 0
			- поднимаем флаг наличия информации GPS
			- при этом продолжаем прием, далее записываем принятые
              байты в буфер и опять инкрементируем счетчик

	- в GPS_PROC:
		- если поднят флаг наличия информации GPS gps_info:
			- сбрасываем флаг наличия информации GPS gps_info
			- копируем исходный буфер в рабочий буфер
			- начинаем обработку:
				- пытаемся выделить корректную пару координат и время
					- если не получили координаты и время:
						- очищаем рабочий буфер
						- остаемся в GPS_PROC
						  ( прилетит еще порция байт , опять поднимется флаг наличия информации GPS
                            и мы заново приступим к обработке)
					- если сработал таймер(GPS "молчит" или нет валидного пакета ) - значит, за 5 сек 
					  (или другое время,которое мы установим) , нам не удалось выделить корректный пакет
					  координат и времени - обработчик таймера описан выше()
					                                 
					- если получили координаты и время:
						- отключить таймер контроля ответа прибора
						- отключить USART_GPS
						- очистить приемный буфер USART_GPS
						- сбросить все необходимые флаги
						
						Далее в описании состояния GPS_PROC в зависимости от режима работы ...		


состояние GPS_PROC - обработка ответа GPS 

	DEBUG отправить в радиолинию команду "Перешел в состояние GPS_PROC".
	DEBUG HAL_Delay(500)

	если поднят флаг наличия информации GPS:
		- сбросить флаг 
		- провести обработку, описанную выше
		- если нет корректных данных координат и времени, ждем дальше
		
		- если есть корректные данные координат и времени:
			- отключить таймер контроля ответа прибора
			- отключить USART_GPS
			- очистить приемный буфер USART_GPS
			- сбросить все необходимые флаги
			- обнулить счетчик ошибок gps_error_counter = 0 
			 ( обнуляем при каждом корректном приеме данных)
			 
		

			Если мы в режиме тестирования ( ReqMode == MODE_TEST):			
				
				- зафиксировать полученную координату ( координата старта)
				- выделить текущее время из пакета GPS и произвести синхронизацию RTC			
				- передать в радиолинию сообщение с полученными координатами и временем  ("Координата, время, вне области")
				- перейти в состояние 4  drone_state = REQ_LIDAR 
				
				
					
				Прим:  начальная координата и время нужны для оператора - если включен спуфинг и значение 
					   координат и времени нереальное, то работа системы "ДРОН-1" невозможна;
					   не имея ни одной валидной координаты, выявить спуфинг ДРОН не может,
					   решение принимает оператор на основе полученных данных
							
					
			Если мы в режиме ожидания разведки ( ReqMode == MODE_EXPECT):

				- зафиксировать полученную координату ( текущая координата )
				- по полученной и предыдущим координатам и времени провести проверку на спуфинг 
					- если спуфинг выявлен:
						- перейти в состояние GPS_ERROR_PROC							
					
					- если спуфинг не выявлен:
						- по полученной координате провести проверку, зашли мы в область разведки или нет;
							- если мы еще не в области разведки:
								- передать в радиолинию сообщение с полученными координатами и временем  ("Координата, время, вне области")
								- перейти в состояние drone_state = COMMAND_INFO
						
						- если мы уже в области разведки:
							- передать в радиолинию сообщение с полученными координатами и временем  ("Координата, время, в области")
							- перейти в режим разведки  req_mode == MODE_WORK	
							- перейти в состояние REQ_GPS
							  ( проведем цикл измерения и следующее проведем в соответствии 
                                с выбранным режимом разведки )
							- провести настройки RTC вы соответствии с режимом разведки
							
			Если мы в режиме выполнения разведки   req_mode == MODE_WORK:
			
				- зафиксировать полученную координату ( текущая координата )
				- по полученной и предыдущим координатам и времени провести проверку на спуфинг 
					- если спуфинг выявлен:
						- перейти в состояние GPS_ERROR_PROC						
				
					- если спуфинг не выявлен:
						- по полученной координате провести проверку, мы в области разведки или нет;
							- если мы вне области разведки (случайно вылетели, ошибка оператора дрона...):
								- передать в радиолинию сообщение с полученными координатами и временем  ("Координата, время, вне области")
								- перейти в состояние drone_state = COMMAND_INFO
								  ( в любом из трех режимов разведки большую часть времени мы будем в состоянии COMMAND_INFO
								    в ожидании очередного цикла измерения либо команд с земли)
						
							- если мы в области разведки: 
								- сохраняем текущие координаты, расстояние между точками
    							  и время для пакета передачи на землю
								- переходим в состояние REQ_LIDAR ( следующий после GPS)
								
			Если мы в режиме возвращения или "перелета"   req_mode == MODE_RETURN:
				- передать в радиолинию сообщение с полученными координатами и временем  ("Координата, время, вне области")
				- перейти в состояние drone_state = COMMAND_INFO

Формат записи полного накопленного спектра на SD-карту
ID23 (0x17) — итоговый накопленный спектр, 1024 канала.
Смещение (байты)	Размер (байты)			Поле								Формат
0–1							2			Год (YY)								ASCII
2–3							2			Месяц (MM)								ASCII
4–5							2			День (DD)								ASCII
6–7							2			Часы (HH)								ASCII
8–9							2			Минуты (MM)								ASCII
10–11						2			Порядковый номер спектра				uint16_t, Little Endian
12–15						4			Широта GPS начала набора				float, IEEE-754, Little Endian
16–19						4			Долгота GPS начала набора				float, IEEE-754, Little Endian
20–21						2			Высота LIDAR начала набора, см			uint16_t, Little Endian
22–2069						2048		Накопленный спектр, 1024 канала		1024 × uint16_t, Little Endian
Итого						2070		Полезная нагрузка	

Формат строки CSV
Каждый байт записывается двумя шестнадцатеричными символами (00–FF), разделитель — запятая.
17,XX,XX,XX,XX,...,XX\r\n
